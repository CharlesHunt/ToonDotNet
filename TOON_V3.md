# Toon V3 Compliance Audit

## Summary
This audits the current C# implementation against the TOON spec v3.0.x–v3.3.2 rule set (the v3 line, immediately before v4.0.0) — deliberately excluding everything already tracked in [TOON_V4.md](TOON_V4.md). The picture was worse than "a few missing v4 features on an otherwise-solid v3 base": several MUST-level v3 rules were outright violated, including two bugs that broke on the simplest possible inputs (an empty document, and an empty array field written in its own preferred short form) and one that silently dropped data during encoding with no error at all. These were not edge cases reachable only by adversarial input — they were everyday shapes (empty collections, nested arrays, duplicate-safe parsing) that any real dataset would eventually hit. The v4 gap list in TOON_V4.md is substantially about *additive* grammar; this document is about the *existing* v3 grammar being implemented incorrectly.

**Status: the fix-order list (items 1–13) is complete.** All 12 correctness-risk findings are fixed, 5 of 6 interop-risk findings are fixed (findings 14–18), and all 3 minor findings are fixed (findings 19–21). Finding #18 (delimiter scoping) was fixed as a **minimal, deliberately-scoped fix**: value quoting is now delimiter-aware (only the actually-configured delimiter forces quoting, not comma/pipe/tab unconditionally) — full per-array delimiter selection (a distinct document-vs-active-delimiter API surface) was considered and explicitly deferred as out of scope; see the finding's row below for the reasoning. Only finding #13 (canonical empty-array short form) remains open — a standalone, low-priority, never-scheduled interop nicety (the encoder always uses the spec-legal `key[0]:` legacy form rather than the newer `key: []` short form), not part of the fix-order list. See [CHANGELOG.md](CHANGELOG.md) for the release this work landed in.

## Findings by severity

### Correctness risk (wrong/lost data, or crash on valid input) — ✅ all fixed
1. ✅ **Fixed.** Decoding an empty document threw instead of returning `{}` (§5) — broke the most basic round-trip: `Decode(Encode(new {}))` threw. Now returns `{}` (`ToonDecoder.cs`, `Toon.cs`).
2. ✅ **Fixed.** `"[]"` (bare root) and `"key: []"` (canonical empty-array shorthand) decoded as the literal string `"[]"`, not an empty array (§4, §9.1). Now decodes as an empty array (`LiteralUtils.cs`).
3. ✅ **Fixed.** Encoding a non-uniform array containing a nested array-of-arrays as a list item silently dropped that item — no exception, no line written, the value vanished (§9.2, §9.4). `EncodeListItemValue` now has a fallback branch (`ToonEncoder.cs`).
4. ✅ **Fixed.** Empty tokens inside an inline/tabular array (`a,,c`) decoded to `null` instead of empty string `""` (§9.1). Now decodes to `""` (`LiteralUtils.cs`).
5. ✅ **Fixed.** Numeric tokens with leading zeros ("05", "0001", "-05") silently decoded as numbers instead of being treated as strings (§4) — real risk for zip codes, product/serial codes. Now decode as strings, with "0.5"/"0e1"/"-0.5" correctly still decoding as numbers (`LiteralUtils.cs`).
6. ✅ **Fixed.** Malformed array-length headers `[03]` and `[-1]` were silently accepted rather than rejected — `int.TryParse` tolerated both leading zeros and negative values with no additional validation (§6). Now rejected (`ToonParser.cs`).
7. ✅ **Fixed.** A negative array length (from #6) made the row/item loop degenerate to zero iterations, so a corrupted header silently decoded as an empty array instead of erroring. Fixed by the same change as #6.
8. ✅ **Fixed.** Duplicate sibling object keys always resolved via silent last-write-wins, even when `Strict = true` — there was no strict-mode duplicate-key check at all (§8, §14.4). Now throws in strict mode (`ToonDecoder.cs`, `ValidationUtils.cs`).
9. ✅ **Fixed.** Encoding a `NaN`/`Infinity`/`-Infinity` double threw instead of converting to `null` (§3) — `System.Text.Json.JsonSerializer.Serialize` rejected these values by default. Now encodes as `null` via a custom `JsonConverter<double>`/`JsonConverter<float>` (`Normalizer.cs`).
10. ✅ **Fixed.** A nested array header with no explicit delimiter suffix inherited its parent array's delimiter instead of defaulting to comma, directly contradicting the spec's explicit "absence means comma, never inherited" rule (§6). Now defaults to comma (`ToonDecoder.cs`).
11. ✅ **Fixed.** When a tabular array is a list-item object's first field (header placed on the hyphen line), both the encoder and decoder placed/expected rows at `depth+1` instead of the required `depth+2` — colliding with any sibling fields of the same object (§10). Fixed symmetrically on both sides (`ToonEncoder.cs`, `ToonDecoder.cs`).
12. ✅ **Fixed.** `\uXXXX` unicode escapes were entirely unimplemented: other C0 control characters (U+0000–001F besides `\n`/`\r`/`\t`) were emitted raw/unescaped rather than as `\uXXXX` (a real §15 security concern), and an unrecognized escape sequence on decode was silently passed through as literal text instead of being rejected (§7.1). Both now implemented/enforced (`StringUtils.cs`).

### Interop risk (won't round-trip with other v3-conformant implementations) — 5 of 6 fixed
13. Open (low priority, unscheduled). The encoder **never emits the canonical `key: []` / bare `[]` short form**, always using the legacy `key[0]:` form. Not itself a violation (legacy form is MAY-legal), but it means finding #2 is invisible on this library's own self-round-trip and only surfaces when reading documents from another encoder or a hand-written file.
14. ✅ **Fixed.** Key quoting reused the value-quoting rule set (§7.2) instead of §7.3's distinct, stricter identifier pattern (`^[A-Za-z_][A-Za-z0-9_.]*$`). Concrete failures: an unquoted key starting with a digit (`123abc`) or containing an internal space (`first name`) was emitted unquoted, which a stricter external decoder may reject. Now uses `StringUtils.EscapeKey` (`StringUtils.cs`, `Primitives.cs`).
15. ✅ **Fixed.** Value quoting was missing two of the nine required §7.2 MUST-quote conditions: leading/trailing whitespace, and a value equal to or starting with `-`. An encoded string like `"  padded  "` or `"-foo"` was emitted unquoted, and this library's own decoder (via its pervasive `.Trim()` calls) would silently strip the padding back out on read — a real round-trip data-corruption case, not just a theoretical interop gap. Both conditions now added to `ShouldQuoteString` (`StringUtils.cs`).
16. ✅ **Fixed.** Doubles were formatted with `ToString("G17", InvariantCulture)` instead of the shortest round-trippable form. This produced noisy, non-canonical output (e.g. `0.10000000000000001` instead of `0.1`) and could emit scientific notation with an uppercase `E` inside the magnitude range where §2's canonical form forbids any exponent at all. Fixed via `LiteralUtils.FormatCanonicalDouble`: uses the runtime's shortest-round-trip `ToString()` on modern TFMs (`G17` retained on netstandard2.0, which may run on .NET Framework predating the round-trip guarantee), lowercases any exponent marker outside the no-exponent range, and — the part that actually required new logic — expands back to fixed-point notation via `ExpandExponentialNotation` for any value in `[1e-6, 1e21)` where .NET's default format would otherwise still emit an exponent (its switch-over threshold is well below 1e21).
17. ✅ **Fixed.** The "numeric-like" quoting check used `double.TryParse` as a stand-in for the spec's exact regex (`^-?\d+(?:\.\d+)?(?:e[+-]?\d+)?$`). It over-quoted strings `TryParse` merely tolerated (thousands separators, a leading `+`) and under-quoted an all-digit string whose magnitude exceeds `double`'s range — such a string would have been emitted unquoted and misread as a number/overflow by a conformant decoder. Now uses an exact regex (`StringUtils.NumericLikePattern`) instead.
18. ✅ **Fixed (minimal scope).** No document-delimiter vs. active-delimiter distinction was modeled anywhere — `EncodeOptions.Delimiter` is still a single value for the whole encode call (true per-array delimiter selection was evaluated and explicitly deferred — see below), but value-quoting ignored it entirely: `ShouldQuoteString` unconditionally quoted for comma, pipe, *and* tab regardless of which delimiter was configured, even though `LiteralUtils.FormatPrimitive` already received a `delimiter` parameter — it just never forwarded it to `EscapeString`. Fixed by threading `delimiter` through and checking only `c == delimiter` (tab remains always-quoted independently via `char.IsControl`). This closes the over-quoting without introducing new public API surface. **Deferred:** true per-array delimiter selection (letting one `Encode()` call use different delimiters for different nested arrays) is a distinct, larger design question — no API shape for it was designed, and it remains a prerequisite for [TOON_V4.md](TOON_V4.md)'s `SpecVersion`/delimiter discussion if that's ever pursued.

### Minor / spec-purity — 3 of 3 fixed
19. ✅ **Fixed.** Blank-line-inside-array strict validation (`ValidateNoBlankLinesInRange`) only checked the range immediately after an array's header line — a blank line between row 2 and row 3 of a multi-row array was never detected, even in strict mode (§12). Fixed in `DecodeArrayFromHeader` (`ToonDecoder.cs`): the check now runs after the tabular/list decode loop completes, spanning the header line through the last row/item actually consumed, instead of just the header-to-first-row gap.
20. ✅ **Fixed.** A malformed bracket segment (non-numeric length content, e.g. `[bar]`) always threw unconditionally, regardless of `Strict`. Spec's non-strict mode permits (but doesn't require) graceful fall-through to key-value parsing instead of a hard error. `ParseArrayHeaderLine` (`ToonParser.cs`) now takes a `strict` parameter (default `true`); non-strict mode catches the malformed-bracket exception and returns `null`, letting the caller fall through to its existing key-value parsing path — strict mode is unchanged.
21. ✅ **Fixed.** CRLF line endings were tolerated only incidentally via pervasive `.Trim()` calls scattered through downstream parsing, not deliberately normalized at the scanner boundary ([ToonScanner.cs](src/Toon.DotNet/Decode/ToonScanner.cs) split only on `\n`). Worked at the time, but was fragile — a future change to any one of those `.Trim()` call sites could have silently reintroduced a stray `\r`. Fixed by stripping a trailing `\r` from each line immediately after splitting, before any other processing — `ParsedLine.Raw`/`Content` are now guaranteed `\r`-free rather than relying on downstream trims as a side effect. The existing `.Trim()` calls were left in place (they still serve legitimate whitespace-tolerance purposes per §12); they're just no longer the only thing preventing a stray `\r`.

### Confirmed correct — no gap found
- **§16 Internationalization**: number formatting and parsing both explicitly use `CultureInfo.InvariantCulture` throughout ([LiteralUtils.cs](src/Toon.DotNet/Shared/LiteralUtils.cs)) — no locale-dependent formatting risk.
- **§13.4 Key folding / path expansion, "off" mode**: dotted keys (`user.name`) are correctly treated as a single literal key on both encode and decode — no accidental splitting/expansion anywhere in [ToonParser.cs](src/Toon.DotNet/Decode/ToonParser.cs) or [ToonEncoder.cs](src/Toon.DotNet/Encode/ToonEncoder.cs). Their total absence from the codebase (noted in TOON_V4.md) is genuinely spec-compliant, not a gap.
- **§7.4 missing colon after key**: correctly rejected in both `ParseUnquotedKey` and `ParseQuotedKey`.
- **§9.1 strict count enforcement**: inline array value counts are correctly validated against declared `N` via `ValidationUtils.AssertExpectedCount`.
- **§12 strict indentation**: exact-multiple-of-`indentSize` and tab-in-indentation checks are both correctly implemented and gated on `Strict`.
- **§7.1 unterminated strings**: correctly rejected via `FindClosingQuote` returning `-1` at every call site.

## Recommended fix order
Ordered by (a) correctness/interop risk first, (b) cheap and local before structural, consistent with the working hypothesis that these should land before v4 work starts. Items 1–8 are done; two finding-number references below (items 6 and 7) have been corrected from the original draft, which mislabeled them.

1. ✅ **Done.** Empty document → `{}` and `[]`/`key: []` → empty array (findings 1–2, 13).
2. ✅ **Done.** Empty inline token → `""` not `null` (finding 4).
3. ✅ **Done.** Leading-zero and malformed-length rejection (findings 5–7).
4. ✅ **Done.** Duplicate-key strict check (finding 8).
5. ✅ **Done.** NaN/Infinity → `null` (finding 9).
6. ✅ **Done.** Silent data loss on non-uniform nested array list items (finding 3, not 11 as originally mislabeled) — added the missing fallback case in `EncodeListItemValue`.
7. ✅ **Done.** Delimiter-inheritance fix (finding 10) and §10 tabular-first-field depth fix (finding 11, not 12 as originally mislabeled) — both required touching shared encode/decode logic; fixed symmetrically on both sides with round-trip tests written first.
8. ✅ **Done.** `\uXXXX` escape support + reject unrecognized escapes (finding 12) — landed before starting the v4 gap list, per the original sequencing rationale.
9. ✅ **Done.** Key-quoting rule split (§7.3 vs §7.2) and the two missing §7.2 quoting conditions (findings 14–15) — added `StringUtils.EscapeKey` (§7.3's `^[A-Za-z_][A-Za-z0-9_.]*$` pattern, shared quote/escape logic with `EscapeString` via a new `QuoteAndEscape` helper) and the leading/trailing-whitespace and starts-with-`-` conditions to `ShouldQuoteString`.
10. ✅ **Done (minimal scope, by deliberate choice).** Document/active delimiter scoping (finding 18) was evaluated with three options presented: (a) a minimal fix making value-quoting delimiter-aware, (b) full per-array delimiter selection with new `EncodeOptions` API surface, or (c) defer entirely. Option (a) was chosen — closes the over-quoting gap with no new public API. Option (b) remains a prerequisite for TOON_V4.md's per-array delimiter needs if that's pursued later; it was not designed here.
11. ✅ **Done.** Number canonical-form formatting (finding 16) and numeric-like regex precision (finding 17). `LiteralUtils.FormatCanonicalDouble` replaced `G17` with the runtime's shortest round-trippable `ToString()` on modern TFMs (kept `G17` under `#if NETSTANDARD2_0`, which may run on .NET Framework predating the round-trip guarantee), and added `ExpandExponentialNotation` to convert back to fixed-point for any value in `[1e-6, 1e21)` where .NET's default format still emits an exponent — that conversion turned out to be necessary, not optional, since .NET's switch-over threshold (~1e17) sits well inside spec's no-exponent range. `StringUtils.ShouldQuoteString`'s numeric-like check now uses the spec's exact regex instead of `double.TryParse`.
12. ✅ **Done.** Blank-lines-inside-array full-range validation and malformed-bracket non-strict fallback (findings 19–20). `DecodeArrayFromHeader` now validates the blank-line range after the full row/item loop completes rather than only checking the header-to-first-row gap. `ParseArrayHeaderLine` gained a `strict` parameter (default `true`); non-strict callers now get `null` (fall through to key-value parsing) instead of a thrown exception for a malformed bracket segment — all 4 call sites in `ToonDecoder.cs` now pass `options.Strict`.
13. ✅ **Done.** Explicit CRLF normalization at the scanner boundary (finding 21). `ToonScanner.ToParsedLines` now strips a trailing `\r` from each line immediately after splitting on `\n`, before any other processing — `ParsedLine.Raw`/`Content` are deliberately `\r`-free rather than relying on downstream `.Trim()` calls as an accidental side effect. Defensive hardening; no observed bug, but closes the risk described in the finding.
